# 日本語Webデザイン補助

依頼されたデザインとブランドを保ち、日本語の実文を読んで調整する。別のデザインスキルと併用できる。単独では色、レイアウト、ブランドの方向性を一つに固定しない。

## 進め方

対象の画面、利用者、目的、既存のデザインシステムを把握する。日本語だから和風の配色や縦書きにする、日本の利用者だから高密度にする、と決めつけない。既存スキルから渡された案があれば、それを出発点として日本語部分を見直す。スキル同士が自動で所定の順に動くとは仮定しない。

当てはまる参照だけ読む。各項目には適用場面、根拠の種類、例外、確認方法がある。

## 最初に見るところ

実際の日本語を入れ、次の順で一つずつ確認する。既に満たしていれば変更しない。

1. 日本語に適用されている書体を確認する（T01）。
2. 見出しの行高と改行を、最も狭い対象幅で読む（T04・C02・C03）。
3. 日本語の見出しから内容を拾えるか、条件と操作が同じまとまりにあるか確認する（L01・L04）。
4. 操作ラベルと実際の処理を合わせる。入力があればIMEを確認する（W01・F01）。
5. 実文が欠けないことを、文字拡大と長い名称で確認する（A02・R05）。

具体的なCSSや実装例が必要なら [recipes.md](references/recipes.md) を読む。

短いLPでも、まず `typography.md` と `composition.md` で日本語の実文を確認する。フォームがなければフォーム資料を一括で読まない。根拠の位置づけを確かめるときは [sources.md](references/sources.md)、追加スキルの効果を評価するときは [evaluation.md](references/evaluation.md) を使う。

## 判断の基準

「技術仕様・標準の解説」はCSSやHTML等の動作と標準の条件を説明する。「公開実践」はその組織の用途に基づく。「編集上の仮説」は比較の出発点であり、改善を保証する規則ではない。企業のサイズ基準、本文の行高の目安、文字数の目安を全ての日本語サイトに強制しない。

欧文向けの極端に狭い行高、本文全体の `keep-all`、広い字間の大文字ラベル、日本語を含まないフォント見本を、そのまま和文に当てはめていないか見る。調整のために、コピーの条件や意味を削らない。新しいCSS機能は対応状況と無効時の表示を確認する。

実装するときは、対象の技術と既存のコンポーネントを使う。[starter.css](assets/starter.css) は一例であり、自動で読み込んだり全画面に上書きしたりしない。Webフォントの追加やネット接続も必須ではない。

## 確認と報告

実文、長い見出し、括弧と数字、長い英語を使い、狭い幅、通常幅、文字拡大で確認する。フォームは変換確定Enter、貼り付け、エラー後の入力保持を扱う。ブラウザや実機を操作できなければ、確認できたコードと未確認の動作を分ける。

指摘は、対象箇所、ルールID、観測した問題、利用者への影響、修正案、確認方法で伝える。美的な好みと入力の喪失・操作不能を分け、既存の方針と食い違う目安には理由を付ける。例外を認めた項目と未確認事項も残す。

レビュー結果の構造例は次のとおり。依頼された出力形式があればそちらを優先する。

```json
{
  "target": "料金ページの見出し",
  "rule": "C03",
  "status": "change",
  "evidence": "狭い画面で最後の一字だけが三行目に出る",
  "proposal": "コピーの意味を保ち、幅と文字サイズを比較する",
  "verification": "対象幅で改行と隣接する説明を確認する"
}
```

`status` は `change`、`keep`、`not-applicable`、`unverified` で区別する。未実施の評価、全ブラウザ対応、WCAG全体への適合、CVRや滞在時間の改善は保証しない。
